# RetryRail deployment runbook

This runbook creates an isolated, synthetic reviewer sandbox. It is designed to
make the submitted system easy to inspect without weakening RetryRail's
authority boundaries or publishing provider credentials.

## Decision

Use **Render Blueprint** for the Buildathon deployment.

RetryRail is not only a static React site. Its demonstrated architecture needs
a long-running FastAPI process, a resident transactional-outbox worker and a
durable PostgreSQL database. Render can provision those three resources from
one reviewed `render.yaml`, keep them in the same Singapore region and inject a
private database connection. The compiled React application is served by the
FastAPI service on the same origin, which removes a cross-provider CORS and
configuration failure mode.

Vercel remains excellent for a frontend-only project, but its FastAPI support
runs as a Python Function. Hosting RetryRail there would still require a
separate worker and database provider, so it would make this particular
submission harder to operate and explain.

Authoritative platform references:

- [Render Blueprint specification](https://render.com/docs/blueprint-spec)
- [Render FastAPI guide](https://render.com/docs/deploy-fastapi)
- [Render health checks](https://render.com/docs/health-checks)
- [Render free-instance limits](https://render.com/docs/free)
- [Vercel FastAPI runtime and limitations](https://vercel.com/docs/frameworks/backend/fastapi)

## What the committed Blueprint creates

| Resource | Plan in `render.yaml` | Purpose |
| --- | --- | --- |
| `retryrail-review` | `0.5c-512mb` | Always-on API and compiled control room |
| `retryrail-review-worker` | `0.5c-512mb` | Durable outbox projection and detector refresh |
| `retryrail-review-db` | `0.1c-256mb`, 1 GB | PostgreSQL 16 with public ingress disabled |

This is the recommended judge-facing profile because it avoids the roughly
one-minute cold start of a free Render web service. Render's July 2026 cost
example places an always-on starter web service plus the smallest paid
PostgreSQL instance at about **US$13/month**; the dedicated starter worker makes
the expected RetryRail total roughly **US$20/month**, before unusual bandwidth
or storage growth. Treat that as an estimate and confirm the exact amount shown
by Render before applying the Blueprint.

The free profile is not recommended for final judging: free web services sleep
after inactivity, free PostgreSQL expires after 30 days, and Render does not
offer a free background-worker instance. Monitoring cannot remove those
platform limits.

## Safety profile

The Blueprint deliberately uses `RETRYRAIL_ENVIRONMENT=review`, a separate
validated runtime boundary:

- every secret is generated by Render and never committed;
- the database is reachable only over Render's private network;
- all browser API calls are same-origin;
- the recovery kill switch is mandatory;
- recovery uses the deterministic fake adapter;
- incident analysis uses the deterministic rules fallback;
- Razorpay and OpenAI credentials are neither requested nor accepted;
- replay is limited to the versioned synthetic fixture set; and
- the initial seed is synthetic and every corresponding UI surface labels it.

This reviewer deployment proves the product flow. The separate committed
Razorpay Test Mode receipt proves the real provider boundary. Do not describe
the sandbox as a production deployment or its metrics as live merchant results.

## Deploy

1. In Render, sign in with the GitHub account that can access the RetryRail
   repository.
2. Choose **New → Blueprint**.
3. Connect `abhinavrathee/RetryRail` and keep the Blueprint path as
   `render.yaml`.
4. Review the three resources and the estimated monthly amount. Confirm that
   all resources use `singapore`.
5. Apply the Blueprint. Render will:
   - build the web and API into one digest-pinned multi-stage image;
   - create PostgreSQL 16 with external ingress disabled;
   - run the Alembic migration before replacing the web service;
   - start the dedicated worker;
   - seed the first 400 deliveries of the tuning partition as a healthy
     baseline through authenticated ingestion; and
   - wait for `/health/ready` before considering the web rollout healthy.
6. Wait for both service deploys to become **Live**. The initial synthetic
   projection may take another short interval; refresh until the overview is
   healthy with zero incidents. In the protected Demo view, the reviewer action
   extends that same deterministic stream through delivery 700, opening one
   evidence-backed incident without changing detector logic. The API waits for
   both its bounded worker and the resident worker to settle every projection
   before returning detector evidence; a lease-bound timeout fails closed.

No Razorpay CSV and no OpenAI key should be uploaded to Render for this public
reviewer environment.

## Verify before sharing

Replace `<retryrail-host>` with the hostname Render assigns:

```powershell
$reviewHost = "https://<retryrail-host>"
Invoke-RestMethod "$reviewHost/health/ready"
Invoke-WebRequest "$reviewHost/" -UseBasicParsing | Select-Object StatusCode
```

Expected readiness response:

```json
{"status":"ready","service":"retryrail-api","version":"0.1.0"}
```

Then complete all of these checks:

- open `/` in a private/signed-out browser;
- confirm the page says **Synthetic evidence** and **Test Mode actions only**;
- confirm the API badge says `API ready · v0.1.0`;
- unlock the isolated demo with the generated replay token, run it once and
  confirm the receipt reports one active synthetic incident;
- open an incident directly and refresh that nested URL to prove SPA fallback;
- open `/impact` and verify that the merchant session starts locked;
- confirm `/docs`, `/openapi.json` and `/.env` return 404;
- confirm `/health/ready` returns 200;
- confirm a missing hashed asset returns 404 rather than the application shell;
- capture final screenshots only from this deployed URL; and
- add the verified URL to the README and submission checklist.

Run the protected demo once before sharing the URL. That leaves the single
synthetic incident available for signed-out evidence inspection while approval
and execution controls remain locked. Lock the browser session afterward; do
not publish either generated access value.

For the private recording session, copy the generated
`RETRYRAIL_MERCHANT_APPROVAL_SECRET` and `RETRYRAIL_REPLAY_TOKEN` from the Render
service environment into the in-page unlock dialog. They stay in page memory
and disappear on refresh. Never paste the Razorpay or OpenAI key into the
browser.

## UptimeRobot monitor

Use the existing readiness endpoint; do not add a mutating POST endpoint for a
health check.

| UptimeRobot setting | Value |
| --- | --- |
| Monitor type | HTTP(s) |
| Friendly name | `RetryRail reviewer readiness` |
| URL | `https://<retryrail-host>/health/ready` |
| HTTP method | GET |
| Interval | 5 minutes |
| Expected status | 200 |
| Optional keyword | `"status":"ready"` |

`/health/live` proves only that the HTTP process responds.
`/health/ready` additionally checks PostgreSQL connectivity and the exact
Alembic migration head, so it is the better alert target.

UptimeRobot is monitoring, not availability infrastructure. On the committed
paid profile the service is already always-on. If plans are changed to free,
Render can still restart or suspend resources and the free database still
expires; a ping does not provide an uptime guarantee.

## Rollback and incident response

- Keep `RETRYRAIL_RECOVERY_KILL_SWITCH=true` throughout public review.
- If readiness fails after a deploy, Render keeps the previous healthy web
  version when the pre-deploy migration or health check fails.
- Roll back the web and worker to the same Git commit; never run mismatched
  schema/application revisions.
- If the generated reviewer access values are disclosed, rotate them in Render
  and redeploy. They are not Razorpay or OpenAI credentials.
- If the demo is no longer needed, suspend or delete all three Render resources
  to stop billing. Preserve the Git evidence and screenshots separately.

## Real integrations remain operator-only

The public Blueprint intentionally cannot call Razorpay or OpenAI. A private,
operator-controlled environment can opt into those adapters only after the
corresponding keys are entered directly in its secret manager and all existing
policy/approval gates remain active. Follow:

- [RAZORPAY_TEST_MODE.md](RAZORPAY_TEST_MODE.md)
- [INCIDENT_ANALYST.md](INCIDENT_ANALYST.md)

Never reuse the reviewer environment for live merchant data, and never enable
a live Razorpay key: RetryRail rejects non-Test Mode key identifiers.
